# FUZE One Token Model

## Executive Summary

FUZE One Token Model explains why FUZE uses one ecosystem token only: **FUZE token**.

FUZE token is the single ecosystem token of FUZE. It supports product-connected utility, ecosystem participation, platform alignment, governance direction where applicable, community participation structures, and wallet-based participation ability where activated under required controls.

FUZE does not use a second public token for participation. Wallet-based participation ability is handled inside the single FUZE token model through activation gates, eligibility controls, approved distributable value boundaries, and public risk controls.

The one-token model reduces confusion for users, investors, community members, product customers, partners, contributors, exchange and custody providers, and public readers.

A multi-token model can create unclear rights, unclear demand, unclear utility, unclear accounting, unclear treasury treatment, unclear public communication, and unclear compliance boundaries.

FUZE avoids that by keeping one public ecosystem token and separating it clearly from Platform Credits and stablecoin rails.

FUZE separates:

| System | Public Role |
|---|---|
| FUZE token | Ecosystem participation, alignment, governance direction where applicable, product-connected utility, and wallet-based participation ability where activated |
| Platform Credits | Product usage credits for FUZE products and services |
| Stablecoins | Payment, settlement, treasury, and operational compensation rails |

Wallet-based participation ability is not a second token, not automatic for every wallet, and not active as a guaranteed public payout right. It may apply only to eligible FUZE-holding wallets if the framework becomes active and all legal, accounting, treasury, audit, reporting, smart-contract, eligibility, privacy, and jurisdiction gates are ready.

FUZE token does not guarantee payout, income, dividend, yield, profit, token price, listing, liquidity, market support, exit, game earnings, business revenue, user growth, community growth, approved distributable value, wallet eligibility, or investment return.

## 2. Reader Problem This Paper Solves

Token ecosystems can become difficult to understand when one project uses several public token-like instruments, several rights-based names, several payment systems, and several participation concepts at the same time.

Readers may ask:

- Which token is the ecosystem token?
- Which system is used for product payments?
- Which system is used for stablecoin settlement?
- Which system connects to product utility?
- Which system connects to community participation?
- Which system connects to governance direction where applicable?
- Which system connects to wallet-based participation ability?
- Which system is relevant for exchanges, custody providers, and public reporting?
- Which system creates legal, accounting, or tax review requirements?

FUZE solves this by using one ecosystem token and clear system separation.

The public model is:

| Public Concept | FUZE Position |
|---|---|
| FUZE token | One ecosystem token |
| Platform Credits | Product usage credits |
| Stablecoins | Payment, settlement, treasury, and compensation rails |
| Wallet-based participation ability | Possible activation-gated ability inside the FUZE token framework |
| Approved distributable value | Controlled, reviewed, approved value from defined product revenue pools if the framework becomes active |

This keeps public communication easier to understand.

It also helps product users, partners, investors, and community members avoid confusing product usage with token ownership or payment rails.

## 5. Token, Credits, Stablecoins, and Wallet Relationship

### 5.1 One Token, Three Separated Systems

FUZE separates token ownership, product usage, and payment rails.

| System | What It Does | What It Does Not Do |
|---|---|---|
| FUZE token | Supports ecosystem participation, product-connected utility, alignment, governance direction where applicable, and wallet-based participation ability where activated | Does not guarantee payout, income, yield, listing, liquidity, price, or exit |
| Platform Credits | Support product usage across FUZE products and services | Do not create token ownership, governance rights, payout rights, wallet-based participation eligibility, or investment exposure |
| Stablecoins | Support payment, settlement, treasury, vendor payment, contributor payment, and operational compensation | Do not create FUZE token ownership or automatic participation rights |

This separation protects product users, token holders, contributors, partners, community members, and public readers from confusing product usage with token ownership or payment rails.

### 5.2 Wallet-Based Participation Ability Inside the One-Token Model

Wallet-based participation ability is a possible FUZE token-related framework where eligible FUZE-holding wallets may participate in approved distributable value from defined FUZE product revenue pools if the framework becomes active.

This ability is inside the one-token model.

It is:

- FUZE token-related
- wallet-based
- eligibility-controlled
- activation-gated
- dependent on defined product revenue pools
- dependent on approved distributable value
- dependent on legal, accounting, treasury, audit, reporting, smart-contract, eligibility, privacy, and jurisdiction readiness

It is not:

- a second token
- a separate public participation unit
- automatic for every wallet
- active as a guaranteed public payout right
- based on gross revenue
- based on token sale proceeds
- based on seed-round funds
- based on game rewards
- based on general treasury balance

Holding FUZE token alone does not automatically create wallet-based participation eligibility.

### 5.3 Eligibility Is Controlled

Eligibility, where activated, may depend on defined rules.

Potential eligibility factors may include:

| Eligibility Area | Public Meaning |
|---|---|
| FUZE token holding status | Wallet may need to hold FUZE under defined rules |
| Wallet type | Self-custody, exchange custody, contract wallet, or other wallet types may be treated differently |
| Snapshot record | Eligibility may use defined snapshot records where applicable |
| Vesting or lock status | Restricted or locked tokens may have separate treatment |
| Jurisdiction rules | Eligibility may depend on country, residency, legal status, or restricted territories |
| Private verification | Some cases may require private verification while keeping personal identity off public records |
| Custody treatment | Exchange-held tokens may need separate proof or claim treatment |
| Transfer rules | Some participation frameworks may require transfer restrictions or eligibility controls |
| Participation agreement | Some frameworks may require accepted terms where applicable |
| Legal and compliance review | Eligibility depends on final legal and compliance review |
| Treasury and audit rules | Eligibility depends on treasury and audit readiness where value movement is involved |

The following actions do not automatically create eligibility:

- buying FUZE token
- holding FUZE token
- receiving FUZE token

- joining FUZE community

Eligibility exists only under defined, reviewed, and activated rules.

| Privacy gate | Separates public wallet records from private identity records |

| Governance gate | Ensures approval path is defined before activation |

These gates protect users, token holders, the community, partners, and FUZE public communication.
