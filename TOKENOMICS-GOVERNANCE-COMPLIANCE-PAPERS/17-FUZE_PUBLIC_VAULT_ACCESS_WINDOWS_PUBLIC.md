# FUZE Public Vault Access Windows

## Executive Summary

FUZE Public Vault Access Windows explains how FUZE may use controlled, eligibility-gated, market-aligned, lockup-aware, and compliance-reviewed access windows for selected vault-token access where final policy allows.

FUZE uses one ecosystem token only: **FUZE token**.

FUZE token is the single ecosystem token of FUZE. It supports product-connected utility, ecosystem participation, platform alignment, governance direction where applicable, community participation structures, and wallet-based participation ability where activated under final policy.

Public Vault Access Windows are different from Public Vault Visibility.

Public Vault Visibility means public-safe transparency into selected vaults, wallet labels, records, report hashes, audit references, release status, reserve status, and governance references.

Public Vault Access Windows mean controlled access windows for selected vault-token access where final policy allows.

Visibility can exist without access.

Access must not be assumed from visibility.

Public Vault Access Windows may show:

- source vault;
- access window;
- purpose;
- eligible participant categories;
- jurisdiction status;
- token amount;
- pricing method;
- access limits;
- lockup rules;
- proceeds destination;
- contract reference;
- policy reference;
- status;
- public risk boundary.

FUZE does not describe Public Vault Access Windows as unrestricted public buying. FUZE describes them as **publicly visible, eligibility-controlled access windows**.

Public Vault Access Windows are not a public investment offer, public solicitation, listing substitute, liquidity assurance system, token price promise, payout system, dividend system, yield system, or financial-return plan.

Platform Credits are product usage credits and are separate from FUZE token.

Stablecoins are payment, settlement, treasury, and operational compensation rails.

Wallet-based participation ability is not a second token, not automatic for every wallet, and not active as a guaranteed public payout right.

FUZE does not guarantee payout, income, dividend, yield, profit, token price, listing, liquidity, market support, trading volume, exit, game earnings, business revenue, user growth, community growth, approved distributable value, wallet eligibility, Public Vault Access Window availability, smart-contract security, AI accuracy, or investment return.

## 4. FUZE Public Vault Access Window Model

### 4.1 Definition

A Public Vault Access Window is a controlled access window for selected FUZE tokens from an approved source vault.

| Element | Public Meaning |
|---|---|
| Source vault | The allocation vault from which selected tokens can be accessed |
| Access window | A defined time-based or condition-based period where eligible participants can participate |
| Eligibility control | Rules that define who can access the window |
| Market-aligned pricing | Pricing method connected to approved policy and market-aligned logic where applicable |
| Purchase / access limits | Maximum or minimum access amounts where policy requires |
| Lockup | Holding or release restriction designed to support controlled circulation |
| Compliance gate | Legal, jurisdiction, eligibility, and policy controls where applicable |
| Contract reference | Public contract, vault, or transaction reference where available |
| Policy reference | Public policy hash, document reference, or governance record where available |
| Proceeds destination | Public explanation of where proceeds go where applicable |
| Public history | Transaction and access records shown where public-safe and technically available |
| Risk boundary | Public explanation of what the access window does and does not imply |

Public Vault Access Windows give readers a clearer view of why selected tokens move, where they come from, who can access them, what controls apply, and what risks remain.

### 4.2 Core Purpose

Public Vault Access Windows have five primary public purposes.

| Purpose | Public Role |
|---|---|
| Transparency | Shows selected access windows instead of hidden vault movement |
| Controlled circulation | Keeps releases tied to policy, lockups, pricing, eligibility, and reporting |
| Market alignment | Avoids arbitrary pricing and supports market-aligned access rules where final policy allows |
| Eligibility discipline | Limits access to qualified participants under legal and platform controls |
| Product-first utility | Keeps access connected to FUZE platform activity, ZAGA utility, ecosystem participation, and public documentation |

Public Vault Access Windows improve public visibility without turning selected token access into unrestricted public buying.

### 4.3 Public Vault Access Windows vs Public Vault Visibility

FUZE separates visibility from access.

| Concept | Meaning | Public Boundary |
|---|---|---|
| Public Vault Visibility | Public-safe visibility into selected vaults, wallet labels, records, release status, report hashes, audit references, conversion proof, multisig controls, timelock controls, and reserve status | Visibility only; not access, claim, payout, or control |
| Public Vault Access Windows | Controlled access windows for selected vault-token access where final policy allows | Eligibility-controlled; not unrestricted public buying, not investment offer, and not return promise |

A public reader may see a vault without being able to access its tokens.

A public reader may see a source vault used in an access window only if an approved access window exists.

Visibility explains. Access windows govern selected participation.

### 5.3 Market-Aligned Pricing

Public Vault Access Windows can use market-aligned pricing where final policy allows.

Market-aligned pricing exists to avoid arbitrary discounts, hidden preferential pricing, unfair insider access, and unclear private access.

| Pricing Area | Public Role |
|---|---|
| Approved price policy | Pricing rule approved under FUZE governance and public policy controls |
| Signed approved price | Policy-approved price signed or authorized by approved governance controls |
| Minimum price floor | Lower bound that prevents selected access from being priced below approved policy |
| Reference price | Signed price, market reference, TWAP, or other approved reference where applicable |
| TWAP reference | Time-weighted average price reference where sufficient market maturity exists |
| Premium multiplier | Policy-based adjustment above a reference price where applicable |
| Deviation check | Control that detects abnormal price divergence or unreliable market conditions |
| Purchase cap | Limit per account, wallet, access window, participant class, or policy period |
| Lockup | Restriction that delays full active circulation after access |
| Policy reference | Public policy document, hash, governance record, or approval reference |
| Public reporting | Public-safe disclosure of pricing method, access window status, and access history |

Market-aligned pricing is a control mechanism, not a price prediction.

### 5.4 Staged Pricing Model

FUZE can use staged pricing because market maturity changes over time.

| Stage | Pricing Model | Public Role |
|---|---|---|
| Early-stage / low-liquidity stage | Signed approved price, minimum price floor, purchase caps, lockups, and policy approval | Uses policy controls when reliable market references are not mature enough |
| Transitional stage | Signed reference price, market reference where available, deviation checks, caps, lockups, and reporting | Combines approved policy with emerging market context |
| Mature market stage | TWAP reference, premium multiplier where applicable, minimum floor, deviation checks, caps, lockups, and public reporting | Uses market data as a reference where reliable |
| Exceptional policy stage | Paused, manually reviewed, or governance-approved pricing where abnormal conditions exist | Protects the system during unreliable or abnormal conditions |

This staged model prevents FUZE from treating early-stage and mature-stage markets as the same.

Boundary:

A pricing method is not a future market price promise.

### 5.5 Minimum Price Floor

FUZE can use a minimum price floor for selected access windows where policy allows.

| Floor Function | Public Role |
|---|---|
| Prevent underpricing | Reduces hidden-discount concerns |

| Support controlled circulation | Reduces incentive for immediate pressure after access |
| Improve reporting clarity | Gives a visible lower bound where applicable |
| Require policy approval | Keeps floor changes governed |
| Avoid arbitrary access | Prevents silent admin-set pricing |

A minimum price floor is a pricing-control tool.

It is not a promise that the market price will remain above that level.
