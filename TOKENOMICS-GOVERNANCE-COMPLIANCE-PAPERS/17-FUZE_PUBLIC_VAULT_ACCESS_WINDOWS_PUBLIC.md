# FUZE Public Vault Access Windows

## Executive Summary

FUZE Public Vault Access Windows explains how FUZE may use controlled, eligibility-gated, market-aligned, lockup-aware, and compliance-reviewed access windows for selected vault-token access where final policy allows.

FUZE uses one ecosystem token only: **FUZE token**.

FUZE token is the single ecosystem token of FUZE. It supports product-connected utility, ecosystem participation, platform alignment, governance direction where applicable, community participation structures, and wallet-based participation ability where activated under required controls.

Public Vault Access Windows are different from Public Vault Visibility.

| Concept | Public Meaning |
|---|---|
| Public Vault Visibility | Public-safe transparency into selected vaults, wallet labels, records, report hashes, audit references, release status, reserve status, and governance references |
| Public Vault Access Windows | Controlled access windows for selected vault-token access where final policy allows |

Visibility can exist without access.

Access depends on final eligibility, policy, compliance, jurisdiction, lockup, payment, reporting, and governance controls where applicable.

Public Vault Access Windows may show:

- source vault
- access window
- purpose
- eligible participant categories
- jurisdiction status
- token amount
- pricing method
- access limits
- lockup rules
- proceeds destination
- contract reference
- policy reference
- window status
- public boundary

FUZE describes Public Vault Access Windows as **publicly visible, eligibility-controlled access windows**.

They are not unrestricted public buying, not a listing substitute, not a liquidity assurance system, and not a financial-return plan.

Platform Credits are product usage credits and are separate from FUZE token.

Stablecoins are payment, settlement, treasury, and operational compensation rails.

Wallet-based participation ability is a separate activation-gated framework inside the FUZE token model.

FUZE does not guarantee payout, income, dividend, yield, profit, token price, listing, liquidity, market support, trading volume, exit, game earnings, business revenue, user growth, community growth, approved distributable value, wallet eligibility, Public Vault Access Window availability, smart-contract security, AI accuracy, or investment return.

## 2. Reader Problem This Paper Solves

Public vault visibility can show that a vault exists.

That does not mean people can access the vault.

A community member, product user, partner, contributor, investor, exchange reviewer, or public reader may ask:

- Does public vault visibility create public access?
- Which vaults can support access windows?
- Who can participate in an access window?
- Is access based on community status, product usage, wallet status, jurisdiction, or approved rules?
- How does pricing work?
- Are access windows the same as public investment offers?
- Are access windows the same as wallet-based participation ability?
- Are access windows the same as approved distributable value?
- Can an access window support controlled circulation?
- What happens if a window is paused, closed, or rejected?

This paper solves that problem by defining Public Vault Access Windows as controlled windows for selected vault-token access where final policy allows.

The key answer is:

Public Vault Access Windows are public-facing only when approved, active, and properly controlled. They require source vault clarity, eligibility rules, pricing rules, lockups, compliance review, jurisdiction review, public reporting, and risk boundaries.

## 4. Core Model

### 4.1 Definition

A Public Vault Access Window is a controlled access window for selected FUZE tokens from an approved source vault.

| Element | Public Meaning |
|---|---|
| Source vault | The allocation vault from which selected tokens can be accessed |
| Access window | A defined time-based or condition-based period where eligible participants can participate |
| Eligibility control | Rules that define who can access the window |
| Market-aligned pricing | Pricing method connected to approved policy and market-aligned logic where applicable |
| Purchase / access limits | Maximum or minimum access amounts where policy requires |
| Lockup | Holding or release restriction designed to support controlled circulation |
| Compliance gate | Legal, jurisdiction, eligibility, and policy controls where applicable |
| Contract reference | Public contract, vault, or transaction reference where available |
| Policy reference | Public policy hash, document reference, or governance record where available |
| Proceeds destination | Public explanation of where proceeds go where applicable |
| Public history | Transaction and access records shown where public-safe and technically available |
| Risk boundary | Public explanation of what the access window does and does not imply |

Public Vault Access Windows give readers a clearer view of why selected tokens move, where they come from, who can access them, what controls apply, and what risks remain.

### 4.2 Core Purpose

Public Vault Access Windows have five primary public purposes.

| Purpose | Public Role |
|---|---|
| Transparency | Shows selected access windows instead of hidden vault movement |
| Controlled circulation | Keeps releases tied to policy, lockups, pricing, eligibility, and reporting |
| Market alignment | Avoids arbitrary pricing and supports market-aligned access rules where final policy allows |
| Eligibility discipline | Limits access to qualified participants under legal and platform controls |
| Product-first utility | Keeps access connected to FUZE platform activity, ZAGA utility, ecosystem participation, and public documentation |

Public Vault Access Windows improve public visibility without turning selected token access into unrestricted public buying.

### 4.3 Public Vault Access Windows vs Public Vault Visibility

FUZE separates visibility from access.

| Concept | Meaning | Public Boundary |
|---|---|---|
| Public Vault Visibility | Public-safe visibility into selected vaults, wallet labels, records, release status, report hashes, audit references, conversion proof, multisig controls, timelock controls, and reserve status | Visibility only; access, claim, payout, and control remain separate |
| Public Vault Access Windows | Controlled access windows for selected vault-token access where final policy allows | Eligibility-controlled; not unrestricted public buying, not investment offer, and not return promise |

A public reader may see a vault without being able to access its tokens.

A public reader may see a source vault used in an access window only if an approved access window exists.

Visibility explains.

Access windows govern selected participation.

### 4.4 Source Vault Model

Not every vault fits Public Vault Access Windows.

| Vault / Allocation | Public Vault Access Window Fit |
|---|---|
| Community Participation Allocation | Strong fit where eligible community participation windows are approved |
| Treasury Reserve | Possible fit for controlled strategic access where policy allows |
| Ecosystem Growth & Partnerships | Possible fit for partner or ecosystem access windows where approved |
| Holder Incentives | Generally better suited for earned release rather than public access |
| Liquidity & Market Operations | Generally governed by liquidity and market-operations policy, not normal public access |
| Team Allocation | Not a normal Public Vault Access Window source |
| Advisors / Strategic Contributors | Not a normal Public Vault Access Window source unless governed by contributor policy |
| Foundation Reserve | Generally long-horizon stewardship reserve |
| Transparency / Stability Reserve | Exceptional reserve only under governance controls |
| BOARD / Surfboard Migration | Separate migration claim or eligibility system, not normal public access |

Vault purpose determines whether an access window is appropriate.

Public Vault Access Windows are selective.

### 4.5 Access Window Fields

A Public Vault Access Window can include the following public fields.

| Field | Public Role |
|---|---|
| Window name | Public name of the access window |
| Window type | Community, strategic, ecosystem, partner, contributor, or other approved category |
| Source vault | Which allocation vault supplies the tokens |
| Purpose | Why the access window exists |
| Eligible participants | Who can participate under final rules |
| Jurisdiction status | Where access is available or restricted |
| Token amount | Maximum allocation available in the window |
| Pricing method | Market-aligned method or approved policy pricing |
| Access limits | Per-user, per-wallet, per-community, per-entity, or per-window limits where applicable |
| Lockup rules | Vesting, lockup, staged release, or claim schedule |
| Proceeds destination | Where proceeds go where applicable |
| Contract reference | Smart contract, vault, or transaction reference where available |
| Policy reference | Public policy, approval, hash, or governance reference |
| Window status | Upcoming, active, closed, paused, settled, or archived |
| Risk boundary | Public statement of what access does and does not imply |

This structure makes each access window easier to understand, compare, audit, and report.

This separation keeps the model clear.

Wallet-based participation remains activation-gated.

### 6.1 Eligibility-Controlled Access

Public Vault Access depends on eligibility.

Eligibility can include:

| Eligibility Area | Public Role |
|---|---|
| Account status | Verified account, workspace, or platform identity where applicable |
| Wallet status | Wallet-aware eligibility or recognition where technically and legally ready |
| Jurisdiction | Access limited or restricted by applicable legal and compliance rules |
| Community role | Community participant, contributor, holder, product user, partner, or legacy participant status where applicable |
| Product usage | HerHelp, ZAGA, game, community, or platform usage where product rules allow |
| KYC / KYB | Identity, business, or compliance checks where required |
| Purchase / access limits | Per-user, per-wallet, per-entity, or per-window controls |
| Abuse controls | Anti-sybil, anti-bot, anti-spam, duplicate detection, and risk screening where applicable |
| Lockup agreement | Participant acceptance of lockup or release conditions |
| Policy acknowledgement | Participant acknowledgement of public risk boundaries |

Eligibility keeps the system controlled and policy-aware.

Holding FUZE token does not automatically create access-window eligibility.

Using FUZE products does not automatically create access-window eligibility.

Buying Platform Credits does not automatically create access-window eligibility.

Eligibility exists only under defined, reviewed, approved, and active access-window rules.

### 6.3 Market-Aligned Pricing

Public Vault Access Windows can use market-aligned pricing where final policy allows.

Market-aligned pricing exists to avoid arbitrary discounts, hidden preferential pricing, unfair insider access, and unclear private access.

| Pricing Area | Public Role |
|---|---|
| Approved price policy | Pricing rule approved under FUZE governance and public policy controls |
| Signed approved price | Policy-approved price signed or authorized by approved governance controls |
| Minimum price floor | Lower bound that prevents selected access from being priced below approved policy |
| Reference price | Signed price, market reference, TWAP, or other approved reference where applicable |
| TWAP reference | Time-weighted average price reference where sufficient market maturity exists |
| Premium multiplier | Policy-based adjustment above a reference price where applicable |
| Deviation check | Review process if price differs too much from approved reference |
| Window price | Final approved access-window price where applicable |
| Public report | Public-safe summary of pricing method, not a price forecast |

Market-aligned pricing supports fairness and discipline.

It does not guarantee future token price, market price, listing price, exchange liquidity, resale value, or investment return.

### 6.4 Lockups and Controlled Circulation

Access windows may include lockups, vesting, staged release, or claim schedules.

Lockups can help:

- reduce sudden circulation
- align access with long-term participation
- prevent immediate uncontrolled release
- support product-first participation
- improve public circulation reporting
- reduce misunderstanding around access-window tokens

Lockup design may vary by window type, participant class, jurisdiction, access amount, pricing policy, and final policy review.

### 6.5 Payment and Proceeds Destination

Where an access window includes payment, public reporting may explain proceeds destination in a public-safe way.

Possible proceeds destinations may include:

- product development
- HerHelp launch and operations
- ZAGA product operations
- platform infrastructure
- stablecoin treasury reserve
- legal and accounting review
- security and smart-contract review
- ecosystem support
- liquidity-related operations where approved
- public reporting and transparency systems
- operating runway
- contributor or vendor compensation through approved stablecoin rails

Proceeds destination reporting should be clear, but it should not expose private invoices, payroll records, contributor identities, vendor contracts, investor identities, customer records, legal workpapers, accounting workpapers, or sensitive treasury procedures.

### 6.6 Window Status

A Public Vault Access Window can have clear public status.

| Status | Meaning |
|---|---|
| Planned | Window is being designed but not active |
| Under Review | Window is under legal, compliance, jurisdiction, pricing, treasury, smart-contract, or governance review |
| Approved | Window has approval but is not yet active |
| Active | Eligible participants can access under defined rules |
| Closed | Window is no longer open |
| Paused | Window is temporarily stopped due to review, technical, legal, treasury, or governance reason |
| Settled | Window has completed settlement and reporting |
| Archived | Window remains available as public historical record |

A public status label improves clarity.

It does not create a claim or guarantee access.
